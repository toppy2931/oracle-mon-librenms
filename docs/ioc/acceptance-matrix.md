# 驗收需求對照表（草稿）與能力現況

採購規格書 9.1 要求廠商在正式驗收前提供「驗收需求對照表」，至少含 Requirement ID、適用範圍、前置條件、測試步驟、預期結果、驗收證據、Pass／Fail／N/A 判定。本文件是**廠商側草稿**：先把**有效**需求逐條對上目前的實作，讓缺口與待收集的證據一眼看得出來。簡報與規格的畫面層對照見 [gui-from-proposal-deck.md](gui-from-proposal-deck.md)。

- **對照基準**：master `1c4f1f1`（2026-11-02）。另一個 session 正在做、尚未合併的階段 1a／1b（趨勢視窗、SLA、網路可用性、合規覆蓋率）**不算已做**，標「⏸」。
- **規格書**：`ioc-智慧維運中心資訊服務採購需求規格書_v1.1_紅色不要.docx`。紅字（`EE0000`）＝已刪除、不算需求，442 條刪 143、有效 299；整組被刪的是 AST、CFG、VUL、SAI、CMP、AUT、AI。本表只列有效的 OPS、MON、EVT、LOG、RPT、SLA、NSM、FLW、WEB、ASM 與 IS 的相關條（另列 INT 的三條「不得」條款）。ARC、DEP 與 IS 其餘條款、INT 其餘條款還沒對照。
- **判定欄全部留白（—）**：目前**沒有做過任何正式驗收**。正式驗收需要機關核定的納管清冊、介接清冊、附表 A 參數（F-01～F-31，目前全是「由機關填列」）與驗收測試計畫，這些都還沒有。**N/A 須經機關確認，廠商不得自行免驗**（規格 9.1），所以表中凡是「可能不適用」的項目都只寫「待機關確認」，不填 N/A。
- 「現況」欄是依程式碼與已有紀錄的**預判**，不是驗收結果。一個測試可以同時驗證多項需求（規格 9.1 允許），同列的需求共用同一組步驟。

## 0. 欄位與共通前置條件

| 欄位 | 說明 |
|---|---|
| 需求 | Requirement ID 與一行摘要（不是規格原文） |
| 前置條件 | 先決條件；下列 P1～P5 是共通的，列內只寫額外的 |
| 步驟、預期結果 | 驗收時要做的操作與應看到的結果 |
| 證據 | 「已有」＝目前就有的紀錄（本機測試檔、VM 驗證日期）；「待」＝正式驗收時才收得到的證據（截圖、回應、紀錄） |
| 現況（預判） | **已做**＝預期可 Pass；**部分**＝只能部分 Pass；**缺**＝功能沒做，預期 Fail；**流程**＝廠商服務流程，不是產品功能；**待機關**＝要機關核定或填列參數才能驗 |
| 判定 | Pass／Fail／N/A，現在都是「—」 |

**共通前置條件**
- **P1**：monitor-vm 已部署待驗版本（`sudo ./update.sh`），`sudo -u librenms php system/ioc-db-selftest.php` 全部 PASS。
- **P2**：一個 `admin` 帳號與一個 `global-read` 帳號（檢視者）。
- **P3**：已建立 Graylog 唯讀帳號（`python3 system/graylog-reader.py create`），入口讀得到日誌。
- **P4**：FortiGate 日誌已進 Graylog，IOC 標準化 pipeline 已套用（`python3 system/graylog-pipelines.py plan` 顯示沒有待套用的變更）。
- **P5**：LibreNMS 已納管設備，其中至少一台可以安排離線（或有已離線的設備）。

- **PoC**：已實作，但**沒有 VM 驗證紀錄**，或只驗證一部分、資料範圍有限；要在真實環境或機關核定範圍內驗收後才能升為 READY。
- **GAP**：沒有做、沒有資料來源，或本專案**不宣稱具備**。

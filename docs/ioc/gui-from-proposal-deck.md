# 提案簡報 × 採購規格書 × 程式現況：覆蓋矩陣

來源：`IOC_地政資安智慧維運平台_提案簡報_v2.pptx`（15 張，每張是一整頁圖片，沒有可抽取的文字）與 `ioc-智慧維運中心資訊服務採購需求規格書_v1.1_紅色不要.docx`。
簡報的畫面是**示意圖**：數字（18 個站點、1,284 個資產、72 分…）不是需求，也不是我們的資料。整理的是「畫面要顯示哪些項目、怎麼組織」，再對上規格書的有效需求與目前程式碼。

- **對照基準**：master `1c4f1f1`（2026-11-02）。簡報內容沿用 2026-10-20 的逐張整理與 2026-11-02 核准計畫的記載，**本次沒有重看圖片**；程式現況則是逐項用 `ioc-portal.php` 的 `NAV`、`librenms/ioc/*.php`、`Schema.php` 與 `docs/ioc/*.md` 對照過。
- **進行中、尚未合併**：另一個 session 在別的 worktree 做計畫的階段 1a／1b（趨勢視窗、SLA 達成率、網路可用性、合規覆蓋率、設定頁「服務水準」卡片），**還沒 commit**。這份矩陣不把它算成已做，只標「⏸ 進行中」。
- **規格書**：442 條需求，紅字（顏色 `EE0000`）＝已刪除、不算需求，刪 143、有效 299。整組被刪：AST、CFG、VUL、SAI、CMP、AUT、AI；IS-031～039、061～069、071～080、ARC-006／051～059、INT-041～081、DEP-001～012 也刪（含 IS-078 變更需人工核准）。全有效：OPS、MON、EVT、LOG、FLW、ASM、NSM、WEB、RPT、SLA。**規格欄寫〔刪〕＝該組需求已被刪除，不是驗收項**。
- 逐條驗收對照見 [acceptance-matrix.md](acceptance-matrix.md)（含 READY／PoC／GAP 能力現況）。

依該站點離線設備的比例：0＝正常、<25%＝輕微異常、<50%＝中度異常、≥50%＝嚴重異常。「高風險站點」＝嚴重異常的站點數，輕微與中度顯示在說明裡；只有輕微異常時卡片是黃色，不是綠色。

### 整體風險分數（提案版，可調）

分數 0–100，**越高越好**。三個分項各自 0–100，加權平均：

| 分項 | 權重 | 算法 |
|---|---|---|
| 設備與服務 | 40 | 正常設備數 ÷ 設備總數 |
| 事件處置 | 35 | 100 － 未結案件的扣分（高風險 15、中風險 6、低風險 2；扣到 0 為止） |
| 資料來源 | 25 | 正常接收的來源類型 ÷ 有資料的來源類型（還沒接入的不算進分母） |

等級：分數 ≥ 低風險門檻是低風險、≥ 中等風險門檻是中等風險、其餘高風險。**門檻預設 85／65，管理者可在入口左側「設定」頁自己調**（2026-10-20 使用者要求；規則、存放與壞資料處理見 [phase1.md](phase1.md) §3「設定：風險等級門檻」）。某分項沒有資料（讀不到，或沒有可比的對象，例如沒有任何設備）就不納入，權重由其餘分項重新分配，畫面註明「沒有可用的資料，分數只算其他分項」；三項都沒有就是「無法計算」，不是 100 也不是 0。

monitor-vm 在 2026-10-20 的情況（12/14 設備正常、沒有未結案件、1 類來源正常接收）算出來是 94 分、低風險（快照，不是現況）。

等級門檻在設定頁調；分項權重與事件扣分仍在 `librenms/ioc/RiskScore.php` 開頭的常數（`WEIGHTS`、`CASE_PENALTY`；`DEFAULT_THRESHOLDS` 是沒人設定時的預設門檻），改完跑 `python -m unittest discover -s tests`（測試會把目前的數字釘住，要一起改）。簡報的分項是「資安風險、運行穩定性、合規成熟度、資產風險度」，我們沒有後兩者的資料，所以不照抄。

## 8. 第三批：身分與稽核（2026-10-21）

整合順序第 5 項。使用者選的範圍：帳號與角色統計、稽核軌跡、主機遠端登入（SSH／RDP）、帳號盤點紀錄全部做；**只有 admin 能看**；放在新的導覽項目「身分與稽核」（當時簡報「組態治理」頁的組態備份與差異比對沒有來源、維持停用；2026-10-22 起組態備份另有專屬的「組態備份」導覽項目，見第 11 節）。API：`ioc-identity.php`（`accounts`、`trail`、`hosts`、`review_save`），權限在端點與函式庫兩層都檢查。

**帳號與角色**（`IdentityService`，資料來自 LibreNMS 的 `users`、`model_has_roles`＋`roles`、`users_prefs`、`authlog`）
- 統計都只算**啟用中**的帳號（停用的登不進來，算進去會讓比例失真）：啟用數與停用數、角色分布（甜甜圈圖，一個帳號有多個角色各算一次）、管理者幾位與是誰。
- **雙因子**：只判斷「`users_prefs` 有沒有 `twofactor` 這一筆」，**絕不讀 `value`**（那是密鑰；測試會擋）。列出沒有雙因子的管理者。**只算本機驗證的帳號**：`users.auth_type` 不是 `mysql`（LDAP、SSO 等外部驗證）的帳號雙因子由外部管，本機永遠不會有這一筆，算進分母會把「管理者未啟用」誤報成紅燈；畫面另外寫「另有 N 個外部驗證的帳號不算」，沒有任何本機帳號時顯示「不適用」，不是 0／0。
- **最小權限**：只給事實（管理者幾位、是誰、佔多少），**不替單位判斷幾位算太多**，畫面標「僅供參考」。
- **久未登入的帳號**：LibreNMS 的 `authlog` 預設只保留約 30 天，所以最多只能看近 30 天；登入紀錄比 30 天短就看實際的天數；畫面一律寫出「登入紀錄最早從哪天開始、所以只能判斷近幾天」，不能讓人以為是一年內都沒登入。登入紀錄是空的就是「無法判斷」。authlog 的帳號是登入時打的，與 `users` 比對不分大小寫。**這份名單看的是網頁登入紀錄**：只用 API 權杖的帳號（整合用的服務帳號）不會留下紀錄，會一直出現在名單裡，畫面註明「不代表沒在使用」。
- 簡報的「帳號存取審核」與「定期盤點」是流程、系統裡沒有資料，合併成管理者手動記錄的**帳號盤點紀錄**：最近一次盤點日期（真實日期、不能是未來）、負責人（≤64 字）、盤點週期（預設 90 天，7～365）。畫面算距今幾天，超過週期標黃；沒記錄寫「尚未記錄」。存在 `ioc_settings`（`review.last_date`、`review.owner`、`review.period_days`），每次變動留 `ioc_settings_history`；這些異動**只出現在 admin 才看得到的稽核軌跡**，不會出現在檢視者看得到的風險門檻異動紀錄裡。

**稽核軌跡**（`AuditTrail`）：一張時間表，欄位是時間、操作者、來源位址、類別、動作、結果、說明；可依類別、結果篩選，筆數 50／100／200（伺服器端上限 200，瀏覽器放不大）。來源有四個：
- LibreNMS 登入、登出與失敗（`authlog`，有來源位址）。
- 管理操作（`/var/log/oracle-admin.log`，有來源位址）。只讀檔案最後 256 KB（這個檔案不輪替）；只帶白名單欄位（alias、host、action、cidr、rule、new_ip、old_ip、ip、gw、enabled），**指令輸出與任何其他欄位都不顯示**；動作代碼對照中文，不認得的照原樣。
- 事件案處理（`ioc_case_history`）與設定異動（`ioc_settings_history`），沒有來源位址。
- 時間：`authlog` 與管理操作紀錄是伺服器本地時間，`ioc_*` 是 UTC，各自轉成明確的時間點再排序、顯示台北時間。
- **某個來源讀不到，畫面標「無法取得：來源（原因）」並說「下表不含這些來源的事件，不代表那段時間沒有人做過事」**，其他來源照常列出。檔案不存在是「還沒有人用過管理主控台」（真的沒有紀錄）；檔案存在但 librenms 讀不了才是無法取得。**已知限制**：這個檔是各管理端點自己寫的，寫不進去時端點不會報錯（既有行為），所以「沒有紀錄」不能證明沒有人用過管理主控台，畫面的說明有寫。

**主機的遠端登入**（`HostLoginService`，Graylog）：最近 24 小時 Linux（sshd 規則）與 Windows 的登入成功、登入失敗、無效帳號，各項筆數加最新 50 筆。Linux 與 Windows 的日誌**最近 24 小時都沒收到**時寫「最近 24 小時沒有收到…的日誌（還沒接入，或已經中斷了），不代表沒有人登入」，不顯示空表（這裡分不出「沒接入」與「接入後中斷」，兩種都說）；只收到一種就提醒不含另一種。Windows 的登入成功／失敗含網路登入與服務登入，不能說成 RDP，來源標籤寫「Windows 登入」，Linux 寫「SSH（Linux）」。範例資料與正式資料互相排除（共用 `OverviewService::demoFilter()`，測試會擋各服務自己拼條件）。monitor-vm 目前沒有這兩種日誌，所以現在只會看到這句說明。

**這一批沒做**：VPN、堡壘機、API 的連線方式分類（LibreNMS 不記 API 的使用；VPN 與堡壘機要有設備或日誌來源）；Graylog 自己的使用者與角色（要 admin 帳號才讀得到，唯讀 Token 取不到，入口也不碰 admin 密碼）；帳號的細部權限（裝置群組等）；任何會「改」帳號的動作（停用、換角色）——這一頁只讀。

**〔2026-11-02 更正〕** 下文的「24 小時」「每 4 小時一格」「前一個 24 小時」是 2026-10-21 的原始設計。2026-10-24（`742aa4a`）加上期間選擇後，期間可選 30 分鐘、1、4、8、12、24 小時（預設 24 小時，`NetworkVisibilityService::RANGE_LABELS`），趨勢固定分 6 格（每格＝期間 ÷ 6），「前一期」是「前一個同長度期間」，伺服器端快取依正式／範例與期間各一份。橫向探測門檻（10／25／50 個目的主機）與被擋下次數（100）是固定常數，**不隨期間縮放**；下文的數字都是預設 24 小時下的情況。

**資料來源**：只有 Graylog 的防火牆日誌，而且只用**彙整查詢**（不撈原始訊息）。連接埠與類別用這台既有 FortiGate pipeline 寫的欄位：`cat`（`traffic:forward` 是經過防火牆轉送的連線）、`dstport`。**位元組數不能用它的 `network_bytes`**：VM 實測那個欄位每一筆都是 0（它讀 `sentbyte`／`rcvdbyte`，但這台 FortiGate 的 CEF 把位元組數放在 `out=`、`in=`，見 [existing-graylog-config.md](existing-graylog-config.md)「值得注意」）。所以 IOC 自己的防火牆 pipeline 新增規則 `ioc-fw-bytes`（`system/graylog-pipelines.py`），從原始訊息文字取 ` out=`、` in=`，寫標準欄位 `net_bytes`（數字，送出加收到；沒有 out／in 的日誌不寫，沒有資料≠0），內網可視性讀 `net_bytes`。欄位名稱集中在 `NetworkVisibilityService` 的 `F_*` 常數，換設備廠牌時改那裡。**`net_bytes` 只有套用之後進來的日誌才有，之前的補不回來**：剛套用時趨勢前面幾格是空的（畫面寫「沒有位元組數資料」與原因，24 小時合計與佔比只算有資料的格），Top Talkers 只算有資料之後的日誌，前一個 24 小時沒有資料可比較，24 小時後才完整。限制畫面也寫了：**只看得到經過防火牆的流量**，同一網段內、不經過防火牆的流量看不到（要旁路感測器，目前沒有）。

**內部網段**（`IpNets`、`SettingsService::NET_INTERNAL`）：預設是 RFC1918 私有位址（`IpNets::DEFAULTS`，單一來源），存在 `ioc_settings`（`net.internal_cidrs`，逗號分隔、整理後的 CIDR），每次變動留 `ioc_settings_history`。設定頁新增「內部網段」卡片（一行一個），只有 admin 能存（檢視者看得到但唯讀）。
- 驗證：只收 IPv4；前綴長度 8～32（`/0`～`/7` 幾乎一定是填錯）；沒寫前綴當 `/32`；主機位元非 0 就換成網路位址；排序、去重，所以整理後沒有變動就不寫、不留紀錄；最多 10 個網段；轉成查詢條件後不能超過 256 項。**IPv6 一律不算內部**（畫面註明）。
- Graylog 的查詢沒有 CIDR 比對（欄位不是 IP 型別），所以轉成「以八位元組對齊的前綴」：`10.0.0.0/8` → `10.*`；`172.16.0.0/12` → `172.16.*`…`172.31.*`（16 項）；`/25` 以上展開成完整位址。這樣「內部對內部」的篩選在 Graylog 端完成，總量與趨勢才準，不必把每一對位址撈回來再數（測試用隨機位址對照 CIDR 判斷，確保展開的前綴與 `IpNets::contains()` 完全一致）。
- **資料表裡的值壞了**（手動改過）一律視為壞掉：內網可視性所有區塊標「無法取得」並說原因，設定頁標紅色警告、重新儲存即修復；**絕不悄悄套用預設網段**（不然畫面上的「內部」會跟管理者設定的不一致）。
- 改了網段要清內網可視性與總覽的快取（`ioc_network_cache_forget()`、`ioc_overview_cache_forget()`，測試會擋）。
- **全產品只有一個「內部」的定義**：「資安」頁的「被防火牆阻擋的內部來源」也改成用這份設定（`OverviewService` 多一個內部網段的建構參數，傳 `null` 表示設定讀不到，該區塊標「無法取得」）。以前那裡用寫死的私有位址、迴路、連結本地，現在預設只有 RFC1918；迴路、連結本地、IPv6 位址不算內部（要算請管理者在設定頁加）。

**畫面與規則**（`NetworkVisibilityService`，常數都在檔案開頭，提案版）：
- **東西向流量佔比**：內部對內部的位元組數 ÷ 轉送流量總位元組數，加近 24 小時每 4 小時一格的趨勢（6 格剛好蓋滿 24 小時），與前一個 24 小時比較（寫「高了／低了 N 個百分點」）。
- **Top Talkers**：內部來源依位元組數的前 5 名（長條圖，附占轉送流量的比例與日誌筆數）。來源超過 200 個時標「排名可能漏掉流量大但連線很少的來源」（Graylog 回的是依筆數的前 N 個）。
- **異常連線**（同時用在異常 SMB）：沒有基線可比，只能用規則——
  - **橫向探測**：同一個內部來源、同一個目的埠，24 小時內連到 ≥ 10 個不同的內部主機（`PROBE_MIN`；≥ 25 個中風險、≥ 50 個高風險）。「不同的目的主機數」用 Graylog 的 `card`（基數）指標。
  - **被擋下**：內部對內部的**轉送流量**被防火牆擋下（累積 ≥ 100 次中風險，否則低風險）。已算橫向探測的同一來源同一埠不重複列。**只看 `cat` 是 `traffic:forward` 的 deny**（2026-10-22）：VM 驗證時異常連線清單出現「172.16.1.50 → 172.16.1.255：9900」被擋 576 次，目的是網段廣播位址；實測兩端都在內部網段的日誌全是 `traffic:local`（FortiGate 自己收發的流量：連到防火牆本身、送到廣播位址的封包），沒有任何 forward，所以這類 deny 不是橫向連線、不該算異常。限定 forward 之後，這台目前會是「沒有符合規則的內部異常連線」，與東西向 0% 一致；若之後 FortiGate 真的轉送並擋下內部主機之間的連線，才會出現在清單。建立事件案帶的證據查詢維持原範圍（調查時看同一來源同一埠的全部紀錄）。
  - 廣播與探索類的埠（DHCP 67／68、NetBIOS 137／138、SSDP 1900、mDNS 5353、LLMNR 5355）不算，區網裡天天有。
  - **異常 SMB 來源** ＝ 目的埠 445 被標記的內部來源數，與前一個 24 小時比較（增加／減少 N%、持平、前期為 0）。
  - **目的欄顯示內部主機 IP**（2026-10-22）：前面的分組只知道「連到幾個不同的目的」，所以對清單上的來源與埠再查一次（來源 × 埠 × 目的三層分組：橫向探測類看轉送流量、被擋下類只看被擋下的連線，各最多一次，限定在清單上的來源與埠）；每一列最多列 3 個目的（依筆數、再依位址），其餘寫「等 N 個」，`distinct` 仍是真實的目的數。**補查失敗（逾時、Graylog 不接受三層分組）只會少了 IP，畫面退回「N 個內部主機」，清單本身不受影響；失敗原因放在回傳的 `dst_error`，清單下方會寫出來（不能默默少了 IP）。** 外部位址與缺值的目的不列。
  - 清單最多列 20 筆（嚴重的在前）；被查詢上限截斷（來源層 100 個，或某個來源的埠層 100 個）時標「可能還有沒列出的來源」；不是看「來源 × 埠」的總列數（40 個來源各 3 個埠有 120 列，沒有任何一層碰到上限，不標）。每一筆有「建立事件案」捷徑（只有 admin），預帶事件類型（新增的「內網橫向探測」或既有的「內部來源被防火牆持續阻擋」）、嚴重性、來源位址與證據查詢。
- **IDS 告警**：FortiGate 的 IPS 與異常偵測日誌（`cat` 是 `utm:ips`、`utm:anomaly`）。一筆都沒有時**分不出「沒開 IPS 日誌」與「真的沒有攻擊」**，所以寫「尚未接入」，不顯示 0；有日誌才顯示筆數與較前期的變化。
- **旁路感測器**：沒有，卡片寫「尚未接入」，不畫假架構圖。

**取不到就說原因，不能是 0 或「沒有異常」**（OPS-006）：沒有防火牆日誌、有防火牆日誌卻沒有轉送流量、日誌沒有位元組數（`net_bytes` 不存在或全是 0；pipeline 還沒套用或套用失敗）、日誌沒有目的埠欄位（`dstport`；內部連線有資料、但每一列的埠都是缺值才算，只有一部分缺值——例如 ICMP——不算；否則每一筆都會歸到「沒有連接埠」、445 永遠對不上，異常 SMB 會變成綠色的 0）、Graylog 連不上、內部網段讀不到，各有各的說明；Graylog 連不上時只打一次查詢就讓所有區塊標原因（不會每個區塊各等一次逾時）。前一個 24 小時讀不到只影響「較前期」的比較。查詢的順序就是優先順序（涵蓋 → 熱門來源 → 異常 → IDS → 趨勢），因為整次畫面載入共用 Graylog 的 25 秒時間預算，最花查詢次數的趨勢放最後。一次載入約 20 個 Graylog 查詢，所以有 60 秒的伺服器端快取（正式與範例資料、各期間分開）。

**事件類型目錄**新增「內網橫向探測」（T1046 網路服務探索，提案版文字請調整），現在是 10 類。

**這一批沒做**：不經過防火牆的流量（要旁路感測器）；IDS 感測器與 NSM；以基線判斷異常（沒有基線資料）；IPv6；依站點或網段分組的流量；期間選擇（當時固定 24 小時，現在可選，見上方更正）。

**VM 驗證狀態**：✅ 2026-10-21／22 資料層與畫面（異常連線、IDS 26 筆、`net_bytes`、目的 IP 三層分組、東西向 12%、global-read 打 `save_network` 回 403）；⏳ 期間選擇；Top Talkers 與趨勢畫面沒有明確回報。

## 10. 站點與網段設定（2026-10-22）

起因：monitor-vm 的總覽只有 1 個站點（機房），其餘 13 台設備「沒有有效位置」（LibreNMS 的「位置」多半沒人設，或是 SNMP 預設值）。使用者要在設定頁自己輸入站點名稱與它所使用的網段，讓設備靠 IP 自動歸站點。

**規則**（`Sites`、`Fleet`）：
1. 設備 IP 落在某站點的網段內 → 該站點；網段重疊時前綴長的優先（例如 `172.16.0.0/16` 是總部、其中 `172.16.1.0/24` 是機房，`172.16.1.5` 屬於機房）。
2. 沒符合任何站點網段的設備 → **未歸屬站點**，照舊另外計數、不假裝成站點。**LibreNMS 的位置不再當站點**（2026-10-22 使用者：「站點數請以設定的內容為主要依據」：VM 上設了台南、台中兩個站點，LibreNMS 另有位置「台中機房」的設備，站點數卻顯示 3，和設定對不起來；原本的做法是沒符合網段的設備回頭用 LibreNMS 位置，位置與站點同名時合併）。站點區塊會列出「沒歸屬的設備身上有哪些 LibreNMS 位置」（例如台中機房），提示要納入請到設定頁新增站點與網段，不然那些設備像是憑空消失。
3. **還沒設定任何站點時**，站點才是 LibreNMS 的有效位置（SNMP 預設值不算），與以前完全一樣。
所以只要設定了站點，**站點數＝設定的站點數**（有設備的站點＋沒設備的站點）。「沒有任何站點可顯示」的空狀態說明（站點數、高風險站點、站點分佈、排行四處）共用同一句，並指向「設定」頁。

**設備 IP 的來源**（LibreNMS 原始碼）：`devices.overwrite_ip`（使用者指定，文字）→ `devices.ip`（`varbinary(16)`，`inet_pton` 的二進位；用查詢建構器讀到的是原始位元組，4 位元組是 IPv4、16 位元組是 IPv6 略過）→ `hostname` 若本身是 IPv4。都沒有（IPv6、沒探索過、hostname 是網域名稱）：設定了站點時這台設備就歸不進任何站點（站點只看 IP），沒設定站點時才靠 LibreNMS 位置。轉換集中在 `Fleet::deviceIp()`（有單元測試）。

**設定頁**：「站點與網段」卡片，一個站點一列（名稱、網段一行一個、刪除），「＋ 新增站點」、儲存、最近 10 筆異動紀錄；admin 可改，檢視者唯讀。規則由伺服器驗證並一次回報所有錯誤：名稱 1～32 字、不含 `|` 與控制字元、不能是 SNMP 預設位置、不分大小寫不可重複；網段只收 IPv4、前綴長度 8～32、每站點 ≤ 8 個、**同一個網段不能屬於兩個站點**；最多 50 個站點。存檔後清總覽快取並重載總覽。

**儲存**：不加資料表。`ioc_settings` 一個站點一列，`skey = site.<id>`、`svalue = 名稱|cidr,cidr`（最長約 184 字元）；`SettingsRepo` 新增 `delete()`、鎖定讀取 `allForUpdate()`（`SELECT … FOR UPDATE`）與依前綴篩選的 `recentHistory(…, $keyPrefix)`。異動紀錄一個站點一筆（新增的原值、刪除的新值都是空，畫面寫「（新增）」「（刪除）」；依前綴在資料庫端篩，不受其他設定異動筆數影響），稽核軌跡的「設定異動」認得站點。儲存是**整份取代**：送來的 id 必須是現有站點（不然是別的管理者已經刪掉它，擋下並請重新整理，避免刪除白做），沒送來的現有站點就刪除；內容沒變動的站點不重寫。**id 只增不減、永不重用**：下一個可用 id 記在 `sites.next_id`（不是站點的一列、不留異動紀錄），刪掉最大的站點再新增也不會拿到舊 id，所以「送來的 id 必須是現有站點」的檢查不會被重用的 id 騙過；整份取代用鎖定讀取，兩個管理者同時儲存會排隊。名稱前後的全形空白、不換行空白、零寬字元會被去掉，只有這類字元的名稱視為空白。

**壞資料不悄悄套用**：資料表裡讀不懂的列、id 不合法的列、名稱或網段與前面站點重複的列都算壞。壞掉時總覽改只用 LibreNMS 位置，並在站點數卡片與站點區塊寫「站點設定讀不到，暫時只依 LibreNMS 的位置分站點（原因）」；編輯器標「有 N 筆不合法」，重新儲存會把它們清掉（各留一筆刪除紀錄）。

**總覽的呈現**：站點數、站點分佈、健康度排行、最新事件案的站點、事件案主機對應站點都用新的歸屬；未歸屬設備的說明在有自訂站點時改寫成「沒有歸屬站點（IP 不在任何站點的網段內）」。**站點數＝有設備的站點＋設定了卻沒有設備歸進去的站點**（2026-10-22 VM 驗證時使用者指出：設了台南、台中兩個站點，台中沒有設備，站點數卻顯示 1，對不上；原本的做法是沒有設備的站點不列）。沒有設備的站點沒有健康等級（顯示「正常」會誤導），所以不在站點分佈與高風險站點的計算裡；改在站點數卡片（「其中 N 個還沒有設備歸進去（名稱）」）、站點區塊的說明（多半是網段填錯）與健康度排行（排最後、灰色「尚無設備」）交代。全部站點都沒有設備時，站點數仍是設定的數量（黃色警示並說明去檢查網段），分佈區塊與高風險站點寫原因。只靠網段定義的站點沒有座標，不上散佈圖（座標沿用設備在 LibreNMS 位置上的座標，同一站點有任何設備有座標就用它）。

**這一批沒做**：站點自己的座標欄位；內網可視性（Top Talkers、異常連線）的 IP 旁標站點名；依站點篩選事件案；站點的健康度門檻設定；IPv6 網段。

**VM 驗證狀態**：✅ 2026-10-22（台南公司、台中公司兩個站點：資料層、global-read 打 `save_sites` 回 403、站點數與「尚無設備」、LibreNMS 位置不再當站點，皆在 VM 重看通過）。

## 11. 組態備份（2026-10-22 起，開發完成、**尚未部署驗收**）

原本簡報第 9 張的「組態治理」整頁維持停用；2026-10-22 起改成 admin 專屬的導覽項目「**組態備份**」（`#config`）：集中設備與排程設定、已設定設備查詢、歷史紀錄分頁、指定兩代並排比較、下載原始版本；一般設定頁只保留前往入口。**global-read 看不到、API 回 403；範例模式不讀正式資料**。

**架構**（跟本 repo 其他 admin 動作一樣走固定信任鏈，細節與機密邊界見 [config-backup-worker.md](config-backup-worker.md)）：PHP（`ioc-backup.php`、`ConfigBackupService`）→ 固定的 sudo helper `manage-config-backup.sh` → 降權到專用帳號 `oracle-backup` → Python 工作器 `system/ioc-config-backup.py`。設備位址以 LibreNMS 設備目錄為準，瀏覽器不能指定任意目的位址；憑證只走標準輸入，不放命令列、錯誤訊息或稽核紀錄。狀態存在 `/var/lib/oracle-mon/config-backup`（權限 700）的 SQLite，**不在 LibreNMS 資料庫裡，主機備份要另外包含它**。

- **採集方式**（管理者明確選擇，系統不會在 API 與 SSH 間自動切換）：`oxidized_cli`（Cisco IOS、FortiGate、Juniper Junos、MikroTik RouterOS，SSH 22）、`fortigate_api`（FortiGate REST Token）、`panos_xml_api`（Palo Alto PAN-OS XML API）。Extreme、Aruba AOS-CX、HPE ProCurve 等尚未驗證，不出現在畫面。
- **排程**：固定間隔 1～168 小時，每份政策最多 50 台；**不是**「每天幾點」的週曆排程。`save` 只是儲存，不等於生效（回傳 `pending_apply`）；`test`／`run` 只排入 `queued`，`queued` 不算成功，要等背景 tick 取得**新的**採集時間與有效內容才建版本；超過 15 分鐘未完成算 `timeout`。
- **版本與機密**：原始內容先雜湊偵測變更，網頁只收到遮罩後的差異預覽；首次成功只建基準、未變更仍留執行紀錄、失敗不覆蓋成功版本。原始版本下載是獨立的 POST（`ioc-backup-download.php`，CSRF、admin、每次寫稽核）。遮罩是盡力而為，不保證涵蓋所有廠牌的秘密格式；SQLite 沒有靜態加密。
- **Oxidized REST 固定綁定 `127.0.0.1:8879`、沒有使用者認證**，只能用在可信任的專用 VM，不得對外開放或反向代理。
- **部署**：`install.sh`／`update.sh` 只部署介接檔與 systemd 單元，**不安裝 Oxidized、不啟用服務**；`uninstall.sh` 停服務但保留備份、歷史與帳號。
- **簡報有、這裡沒有**：變更 KPI、高風險判定、核准流程、「標記為待審核」、變更者（刻意不推測）、週曆排程、自動還原、RANCID 適配器（計畫階段 3b；規格 CFG、IS-078 已刪）。

**驗證狀態：⏳ 沒有部署驗收紀錄。** 2026-10-22／23 的 commit 歷史有多次針對 FortiGate 行為的修正（SSH exec、HA 提示字元、`--More--` 分頁、API 備份），但沒有驗收紀錄，所以一律視為未驗收；本機測試（`tests/php/config_backup_test.php`、`tests/test_config_backup*.py`、`tests/js/config_backup_test.js`）通過不代表 VM 與真實設備驗收通過。階段 3a 要使用者授權才在 VM 部署並實機驗收；**驗收前文件與畫面都不得標 READY**。
